# 环境构造

用于制作或修订可执行任务。先读交付契约，环境能力由题目实际工作与所选 agent 决定。

## 从工作要求推导镜像

列出输入/输出格式、应用、解析与重算工具、字体、语言运行时及 agent harness 依赖。原生办公文件应能打开、编辑与重算；依赖在构建时安装并固定版本。基础镜像使用公开可取得的 digest，离线运行先验证所需工具已经存在。终端 harness 的 tmux、Claude Code 的 CLI 与进程工具也属于环境依赖。

构建上下文分开：`environment/` 仅有工具和可见 `input-data/`，建立空的 `/workspace/output/`；参考解、评分代码、rubric 与作者记录放独立目录。独立 verifier 的构建上下文是 `tests/`，镜像须含 `/tests/test.sh`、全部评分依赖及可信输入，不能假设 runner 还会上传测试代码。可从 assets 的两个 Dockerfile 起步，按任务补工具；模板的脚本入口仍需作者实现。

原生 Harbor 以实际安装版本解析 `task.toml`。环境、输入路径、agent 工作目录、参考解和评分器必须一致。预构建镜像标签或 ID 是运行绑定；任务包保留公开可构建配方。镜像更新记录构建配方、输入和实际镜像 digest。

## 模型通道与启动验证

容器内运行的 agent 需要访问模型 endpoint；宿主运行的 agent 或 judge 可通过宿主模型通道访问。根据实际调用位置配置网络，不把所有任务一律设成离线。密钥运行时注入，镜像和题面不含密钥。白名单运行前核验 DNS、外部路由与控制 sidecar 的实际解析配置；模型连通性检查发生在第一次模型请求之前。需要 CUA 时实际验证显示服务、应用、截图与输入接口，并确认所选沙箱后端提供这些能力。

在空环境执行工具版本、输入枚举、原生文件解析/重算和输出写入的 smoke check，再执行真实 agent 安装/启动检查。模型连通性的小请求只能证明通道可用，不能当作题目试解。

记录镜像构建、沙箱申请/启动、agent、评分、产物导出与清理各阶段耗时。阶段预算传递到具体 exec/HTTP 请求；串行耗时与队列等待分别计量。回收只按本次 job 的资源标识操作，成功、异常和取消均执行清理；持久化产物和凭据交由沙箱外的控制层管理。
